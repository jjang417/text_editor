Subject: [PATCH] scsim/gpu_wrapper: send the GPU's real requester BDF to the
 MC instead of a hardcoded 0x100

commlib_chi_transactor discarded the requester BDF the GPU puts on every
gchi read/write request and passed a hardcoded 0x100 to the memory
controller. Once the SMMU actually translates (ATS enabled, guest booted
without iommu.passthrough=1) the MC rejects every GPU access:

  MC READ ABORTED:  cgid=483, adr=0x1_0f958000, validity=NO_VIOLATIONS,
                    req_valid=1, translation_err=1 (err 34 ERANGE)
  MC WRITE ABORTED: cgid=484, adr=0x1_05368000, ... translation_err=1

The read path swallows the error and returns 0xff filler; the write path
routes through send_b_transport(), whose is_response_error() check raises
SC_REPORT_ERROR and takes the whole simulator down with SIGSEGV.

The GPU does send its BDF. hshub_gchi.cpp populate_gchi_req_attr_bdf(),
guarded by NV_LITTER_ENABLE_ATS, packs it into the 16-bit bdf_reqattr
field ("Send out bdf in the req_attr field to c2c") and is instantiated
for all nine opcodes this transactor decodes -- gchi_read_{once,no_snp,
unique} and gchi_write_{no_snp_ptl,no_snp_full,unique_ptl,unique_full,
back_full,evict_full}. decode_read_req()/decode_write_req() simply never
unpacked it.

Because the GPU-side populate is behind a *compile*-time guard, this is
inert on a passthrough boot (identity mapping, BDF unused), which is why
it went unnoticed until ATS was switched on.

Verified on rf_c1g2n2 (rosa + fn102 + GPU_C2C=true + C2C_ATS_ENABLE=true,
RM 630.00 guest), single variable changed -- only this library differs:

                            before      after
  MC ABORTED                     2          0
  send_read_request_to_mc        1         13
  send_write_request_to_mc       1          2
  sending ATS req                4         30
  bdf on MC requests         0x100      0x200
  RM channel test          SIGSEGV     PASSED (124.7 s)

  NoClientAllocTSG/ChannelTest.ChannelAlloc_CeVirtual/0

All 15 MC requests logged "addrType 0x0, bdf 0x200" (addrType 0 =
ATS_SYSMEM). The run also gets much further than before, since
previously the first transaction aborted and the second killed the sim.
This confirms the MC resolves its translation context from gchi_bdf.

Two caveats. The BDF is read as the low 16 bits of bdf_reqattr rather
than BIT_UNPACKed via gchi_bdf, because that type lives in the GPU
tree's generated xlitter headers and is not in this file's include
scope; the layout was confirmed empirically (bdf 0x200 matches the BDF
already printed on the ATS request). And those 16 bits are an overlay --
under cxl_mode the GPU packs gchi_req_attr (kind/comptag/gfid) into the
same field, so this path is only valid on non-CXL configs.

The two cslDebug lines gain "bdf 0x%x" so the value is checkable
straight from simout.txt.

Not addressed here (separate defect): send_b_transport() turning any TLM
error response into a fatal SC_REPORT_ERROR, while the read path ignores
errors entirely. A rejected write should fail the transaction, not abort
the simulator.

+// [ATS-BDF-FIX] Recover the GPU's requester BDF from a request packet.
+//
+// When the GPU fmodel is built with NV_LITTER_ENABLE_ATS it packs its BDF into
+// the 16-bit `bdf_reqattr` field of every gchi read/write request
+// (hshub_gchi.cpp populate_gchi_req_attr_bdf(): "Send out bdf in the req_attr
+// field to c2c"; instantiated for all 3 read + 6 write opcodes this file
+// decodes). This transactor previously discarded that field and passed a
+// hardcoded 0x100 to the MC, so every ATS-translated access was attributed to
+// the wrong requester -- benign under iommu.passthrough=1 (identity mapping,
+// BDF unused) but not once the SMMU actually translates.
+//
+// NOTE: those 16 bits are an overlay. Under cxl_mode the GPU packs
+// gchi_req_attr (kind/comptag/gfid) into the same field instead, so this must
+// only be used on non-CXL configs.
+//
+// The GPU packs a single 16-bit gchi_bdf field, so the raw value IS the BDF --
+// no BIT_UNPACK needed. Done this way deliberately: `gchi_bdf` lives in the
+// GPU tree's generated xlitter headers and is not in this file's include
+// scope, and depending on it would couple the transactor to that header set.
+// Self-checking at runtime: the cslDebug below prints this value, and it must
+// match the `BDF = ...` already printed on the ATS request for the same GPU.

+// legacy 0x100, is not a safe default -- it is the reference-platform value
+// that aliases both GPUs (and the Mellanox function) onto StreamID 0x050100,
+// i.e. exactly the bug this fix removes. Substituting it would silently
+// reintroduce that failure while looking like the original defect. Pass
+// through what the GPU actually sent so a zero shows up as `bdf 0x0` in the
+// log and is diagnosable. (The GPU-side populate is guarded by a *compile*-

+// populated -- no zero was observed across 15 MC requests on round11.)
+static inline uint32_t ats_bdf_from_reqattr(uint32_t reqattr_raw) {
+    return reqattr_raw & 0xFFFFu;
