  And this is what actually explains the "second run" mystery, which none of my earlier theories did:

  - RM Channel test run 1 ATSD subids: 0x116 … 0x42a — all ≤ 0xFFF, so truncation is a no-op and all 14 responses match.
  - RM Channel test run 2 ATSD subids: 0x19f9, 0x19fa — the first ones ≥ 0x1000, so the response comes back truncated and misses.

Analysis:
  From defs/projects.spec:3554:  #define NV_LITTER_ATSD_HSHUB_SUBID_BITWIDTH 12

  The chain:

  1. hshub allocates ATSD subid 0x19f9 (13-bit pool, 0x0000–0x1FFF) and keys its tracker on it <— this is the bug begin here ....
  2. hshub transmits xx2mem_atsd_cmd with subid=0x019f9 <— bug: incorrect subid bit width (13 bits)
  3. The ATSD responder replies mem2xx_ack_cmd with subid=0x009f9 <— correct allocation: bit 12 masked off
  4. process_memsys2hsh_ats_request() looks up 0x9f9, misses <— correct behaviour given bad input
  5. The accessor asserts, then dereferences end() → SIGSEGV crash

In coherent mode RM maps the GR subcontext header through the GH100 static coherent-FB kernel mapping, which cannot map discontiguous surfaces — hence memdescGetContiguity(pMemDesc, AT_CPU) failing and NV_ERR_INSUFFICIENT_RESOURCES surfacing as CUDA's "out of memory". With EnableNUMA: 0 that path is forced and no regkey relaxes it. acos cannot pass in this mode, by design of the limitation, not because of anything in your tray.

The subctx header allocated (discontiguous, as it apparently always is) → coherent mode routes its CPU map through the static path → memdescGetContiguity(pMemDesc, AT_CPU) false → NV_ERR_NOT_SUPPORTED → remapped upward to NV_ERR_INSUFFICIENT_RESOURCES → CUDA reports out-of-memory.
